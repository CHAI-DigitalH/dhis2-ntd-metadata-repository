# Validation

This document covers data plausibility checks for the SL NTD Metadata Repository, implemented as native **DHIS2 Validation Rules** rather than as documentation-only guidance. Validation rules run server-side and surface violations directly in the Data Quality app, unlike the visualization API limitation documented in [setup.md](./setup.md) — this is a DHIS2 feature that works correctly via standard metadata import.

## What's included

`metadata/validation_rules.json`, generated by `tools/build_validation_rules.py`, contains 14 rules:

| Rule | Disease(s) | What it catches |
|---|---|---|
| Coverage Rate implausibly high | LF, Oncho, SCH, STH (4 rules) | Coverage Rate (%) above 110% — almost always a stale or undersized targeted-population denominator, per [indicators.md](./indicators.md)'s Coverage Rate interpretation note |
| Coverage + Refusal Rate exceeds plausible total | LF, Oncho, SCH, STH (4 rules) | Treated and not-treated populations together exceeding 110% of the shared targeted-population denominator — catches data entered against the wrong district/period more sharply than either rate alone |
| Drug wastage and loss exceeds quantity received | Cross-cutting, all 4 PC-NTD drug datasets (1 rule) | A logical impossibility — outflow due to wastage/loss exceeding total inflow, indicating a data entry error or a missing carryover-stock figure |
| Drug stock balance after MDA is negative | Cross-cutting (1 rule) | Negative physical stock, which cannot exist — indicates a sign convention or entry error |
| Trachoma TF/TT prevalence out of range | Trachoma (4 rules) | Prevalence percentages above 100% — a direct transcription error since these are reported as raw survey percentages with no DHIS2-calculated denominator to debug |

## Importing the rules

```
Import/Export → Metadata Import → select metadata/validation_rules.json → JSON format → dry run first
```

Validation rules have no dependencies on visualizations or dashboards, so they can be imported at any point after the relevant data elements and indicators exist — they don't need to wait until the end of the import sequence in [setup.md](./setup.md), but importing them after indicators (step 5 in that sequence) is the natural point since several rules reference indicator UIDs directly.

## Running validation analysis

Once imported, validation rules don't run automatically against existing data — DHIS2 requires you to run a **Validation Analysis** to check historical data, or rely on real-time checks during data entry going forward:

1. **For new data entry**: rules referencing data elements directly (the drug logistics rules) will surface violations in the Data Entry app's validation check before a form is marked complete, if your dataset has validation enabled.
2. **For existing/historical data, or rules referencing indicators**: go to **Data Quality app → Validation Analysis**, select the org units, period range, and validation rule group (or "All" if no group is configured), and run the analysis. This produces a list of every violation across your selected scope — use this immediately after importing real country data per [data-sources.md](./data-sources.md), not just on an ongoing basis, since historical ESPEN/JRSM/TEMF data transcribed by hand is exactly the kind of data these rules are meant to catch problems in.

## If you remapped UIDs during adaptation

**Read this before importing validation rules if you adapted this repository for a country other than Sierra Leone.**

Every rule's `leftSide`/`rightSide` expression references this repository's Sierra Leone reference UIDs directly (e.g. `#{XBa46KPfVob}` for LF Coverage Rate). If you remapped data element or indicator UIDs per [adaptation.md](./adaptation.md) Section 6, these expressions will reference the wrong objects — DHIS2 will either reject the rule on import (if the UID doesn't exist at all) or, more dangerously, **the rule will simply never trigger** if the UID happens to resolve to something else in your instance.

To fix this:

1. Open `tools/build_validation_rules.py`
2. Find every UID referenced in the `expression` fields (search for `#{` to find them all)
3. Replace each with your instance's corresponding UID
4. Re-run the script to regenerate `validation_rules.json` with your UIDs
5. Import the regenerated file

Do not hand-edit the JSON output directly unless you're confident editing DHIS2 validation rule expression syntax correctly — regenerating from the script is safer since it guarantees consistent formatting across all 14 rules.

## Extending the rule set

If you build the tabled visualizations mentioned in [setup.md](./setup.md)'s known limitations (age-strata charts, the drug Gap-by-commodity indicators, etc.), consider whether each new indicator warrants a matching validation rule — not every chart needs one, but anything that's a calculated rate with a plausible bounds (like Coverage Rate) or a logical inflow/outflow relationship (like the drug wastage rule) is a strong candidate. Follow the same pattern in `build_validation_rules.py`: one Python dict per rule, append to the `validation_rules` list, document it in the table above.

## What this does not cover

Validation rules check **plausibility of values already entered** — they do not prevent nonsensical *combinations* of dimensions (e.g. entering LF treatment data against a period before the dataset's earliest valid year), and they do not validate **completeness** (a district with no data at all triggers no rule, since there's nothing to compare). Completeness gaps are better caught via the post-import validation script (`tools/validate_import.py`) and via routine review of the dashboards themselves — an empty chart is its own signal.
