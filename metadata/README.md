# Metadata package

The importable DHIS2 metadata for the SL NTD Metadata Repository.

| File | What it is | Status |
|---|---|---|
| `full_package.json` | The combined metadata package — category combos, option sets, data elements, datasets, indicators, indicator groups, visualizations, maps, dashboards — assembled from dependency exports. Import this (see [../docs/setup.md](../docs/setup.md)). | **Not yet populated** — currently `{}`. Build it from a real instance (below). |
| `validation_rules.json` | 14 data-plausibility validation rules. Generated by [`../tools/build_validation_rules.py`](../tools/build_validation_rules.py); documented in [../docs/validation.md](../docs/validation.md). | Populated (Sierra Leone reference UIDs). |
| `access_scaffold.json` | Generic, instance-agnostic access model: 3 roles (NTD Administrator / Data Entry / Viewer) + 2 groups (NTD Users, NTD Data Entry). Imported by the installer, which then applies sharing. *Not* Sierra Leone accounts. | Populated. |

## How `full_package.json` is produced

It is **not** hand-written. It comes from DHIS2 **dependency exports** off a real
reference instance, because visualization internals (`dataDimensionItems`) only survive a
genuine export/import round-trip — they cannot be reconstructed via the API (see
[../docs/setup.md](../docs/setup.md), "Critical warning").

Procedure (also in [../tools/README.md](../tools/README.md)):

1. On the reference instance, **relativize** every dashboard's charts first (org units →
   level/user, periods → relative). See [../docs/adaptation.md](../docs/adaptation.md) §1.
2. Confirm each dataset in **Maintenance** has its indicators attached, so dependency
   export pulls them.
3. **Import/Export app → Metadata dependency export**, once per dashboard, with **"Skip
   sharing and access settings" ON**. Save each JSON.
4. Merge them into this file:
   ```bash
   python3 ../tools/build_metadata_package.py --in-dir exports/ --out full_package.json
   ```
   (or pull straight from the instance with `--dashboards <uid> ... --base-url ...`).

The result is a single file that DHIS2 imports in one request; the importer resolves
dependency order internally. Adopting countries then run
[`../tools/configure.py`](../tools/configure.py) / the installer to adapt it.

## What is intentionally NOT here

- **Organisation units** — country-specific; set up in the target instance, never shipped.
- **Data values** — no real programme data; see [../docs/data-sources.md](../docs/data-sources.md).
- **User accounts & org-unit scope** — created per-instance after import (the generic *roles
  and groups* in `access_scaffold.json` are shipped; the actual users and their org-unit
  scope are not). Exports use skip-sharing; the installer applies a clean sharing layer.
